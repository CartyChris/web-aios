## 1. The same app on multiple desktops — REAL BUG, fixed

`singleton` was implemented as `windows.find(w => w.appId === appId)`. No workspace in the
comparison. So opening Settings from workspace 3 while Settings sat on workspace 1 did not
open Settings — it *teleported you to workspace 1*. Four desktops, and three of them could
never hold that app.

The rule is now per workspace, in `lib/window-open.ts` (pure, 11 tests). Having five copies
stacked on one desktop is the mess singleton exists to prevent; having one on each desktop
is the entire point of having desktops. A pinned window still counts as the instance for
whichever workspace you are on, because opening a second copy directly on top of a visible
one is the worst of both behaviours.

**Verified live:** Personalize opened on all four workspaces, one each, four distinct
window ids; re-opening on workspace 2 focused the existing one; the active workspace never
changed under the user.

The Dock had the same bug and it was found while checking this one: it filtered by `appId`
alone, so clicking a tile called `restore()` on a window sitting on another workspace — the
tile lit up and nothing appeared. Its `running` set had the same flaw, which also made the
new "open elsewhere" marker unreachable: a guard that excludes exactly the case it exists
for. Both fixed, and the dock now shows a hollow marker for "running, but not here".

## 2. The marquee — REAL, but not in the marquee

The rubber-band code was correct the whole time. What was wrong is what sits on top of it.

The widget layer is `pointer-events-none`, but every widget CARD is `pointer-events-auto`
so its own controls work. A card therefore consumed any press on its large empty areas —
the blank half of a clock, the gaps in a system readout. On the default desktop those
widgets occupy much of the upper-left, which is exactly where someone starts a drag.

Measured rather than guessed: listeners on the surface logged `pointermove, pointermove,
pointerup` for a drag starting over the clock. **No pointerdown ever arrived.**

The first fix attempt was wrong and was backed out: making the widget *body* transparent
still leaves the card catching the press, and making the *card* transparent would kill the
hover that reveals its drag handle.

What works: `DesktopIcons` now asks the document, in the capture phase, whether a press
counts as bare desktop. A widget's empty background does, because that is what it looks
like. Its drag handle, its close button and anything interactive inside it do not. Anything
outside the surface and the widgets — dock, top bar, windows, menus — is untouched.

**Verified live:** a drag starting on the clock widget now selects all five icons; before
the change the identical drag selected nothing. Dragging a widget by its handle still moves
it and does *not* start a marquee.

## 3. Placing desktop icons — NOT a code bug

Pinning worked at every step. Right-click on bare desktop, "Pin an app here…", pick an app;
it lands where you clicked. Driven end to end: five items became six, the icon rendered, the
picker closed, the position matched the click.

I nearly reported this as broken twice, both times because my own test used the wrong CSS
selector — `.glass.fixed`, when the picker's root is `fixed inset-0 z-[9700]` and its
`glass` panel is a child. Absence of evidence was not the finding.

The real problem is discoverability: the gesture is a right-click on *bare* desktop, and
the default layout covers the obvious part of it with widgets — the same widgets that were
eating the marquee. So the Launcher now carries the affordance: hover any app for a pin
button, or right-click the tile. It drops into the first free grid slot rather than on top
of an existing icon, and it does not launch the app.

## 4. The token slider — REAL UX BUG, fixed

The `max` was already 64,000 in code. What is rendered beside the label is the *value*, and
the value was 4,000 — so the control looked unchanged whatever the ceiling was.

It now reads **"4,096 of 64,000 max"**, with quick-set chips at 1k / 4k / 16k / 32k / 64k.

Two further defects the browser surfaced that source review had not:

- The thumb reported **4,096** while React held **4,000**. With `min=256, step=256`, 4,000
  is not a valid step, so the browser snapped the input and the number beside the label
  disagreed with where the handle sat. The default is now 4,096, which is on the step.
- The top chip rendered as **"63k"**: `Math.round(64000/1024)` is 62.5. Dividing a decimal
  ceiling by 1024. The labels are explicit pairs now, not arithmetic.

**Verified live:** label reads `4,096 of 64,000 max`, thumb matches, and the 64k chip sets
the slider to its maximum.
