## What was built

### 1. A free-services layer — `src/lib/services.ts` (25 services, 51 tests)

Public APIs that need no key, no account and no billing. Every other network feature in
this OS is gated behind a secret, which is the right default for a model provider and the
wrong one for a fact: an OS that can do nothing until you paste a key is one most people
close before they see it work.

The module is pure. A service is a URL builder plus a parser, and neither half touches the
network — which is what lets all 25 parsers be driven in Node against recorded payloads.
That is the half that breaks: a public API renames a field, and a parser that quietly
returns `[]` on the new shape is indistinguishable at the call site from "your query had no
matches". Every parser therefore **throws** on a shape it does not recognise, and every
service has a negative control proving it can still say no.

Catalogue: Wikipedia, Wikidata, Open Library, arXiv, Crossref, PubMed, NASA APOD,
Geocoding, Weather, Earthquakes, Air Quality, Sun Times, Exchange Rates (ECB), Crypto
Prices, World Bank, Country Facts, Public Holidays, Wayback Machine, Hacker News, GitHub,
npm, Dictionary, Word Relations, Open Food Facts, Met Museum.

Each entry declares its `reach`: twelve are CORS-enabled and fetched directly, the rest go
through the existing SSRF-guarded `/api/proxy`. A test pins the direct list, because a
service marked `direct` that the browser cannot actually call fails with an opaque network
error indistinguishable from the host being down.

**Bug found by its own test:** the Open Food Facts parser filtered blank rows by comparing
against a `"(unnamed product)"` sentinel that the code never produced — `str("")` returns
`""`, not the fallback. A guard that excludes exactly nothing. Fixed by filtering before
naming.

### 2. A new app — Open Data (`src/apps/OpenData.tsx`)

The only app in the OS that works fully on a cold install. Browse by category, fill the
arguments, read the rows, save to the VFS or export JSON. Every result carries its
provider and licence.

It renders **three** different outcomes rather than one grey box, because they mean
opposite things: *could not reach the provider* (the query was never answered), *the
provider replied in a shape this reader does not know* (the API changed), and *no matches*
(it answered normally and your query matched nothing).

### 3. Live tools for the harness — `src/lib/harness/webtools.ts` (22 tests)

The catalogue, exposed to the agent. Pure: the transport arrives as an injected
`FetchText`, so all 25 can be driven against recorded payloads and a scripted failure.

Every one is `deterministic: false`, which `toolCatalogueText` already renders into the
system prompt as *"do not quote it as a fixed figure"*. That distinction is the point: an
agent that cannot tell an audited number from a live one will eventually put a live one in
a report as though it were audited. Ten are wired into `harness-runtime.ts` by default
(`DEFAULT_WEB_TOOLS`); the harness now offers 20 tools, 10 deterministic and 10 live.

**The bug the skeptical pass found, and the one worth reading.** `annotationsFor()` fails
closed on a tool name whose segments it does not recognise, and `web_wikipedia` is one — it
came back `destructive: true, requiresApproval: true`. The first version of this module
overrode `readOnly`, `destructive` and `openWorld` and forgot `requiresApproval`. With the
shipped `approvals: "destructive"` policy and `harness-runtime.ts`'s deny-by-default
approver, **every live tool would have been refused before it ran** — and the agent would
have reasoned from the refusal. A pure §7 self-defeating guard: a check that excludes
exactly the inputs the feature exists to serve.

An annotation assertion alone would not have caught it, because the denial happens inside
the loop from the interaction of three separate things. The test that pins it drives the
real `runReAct` under `DEFAULT_LOOP_CONFIG` with `approve: async () => null`, and it was
confirmed to FAIL when `requiresApproval` is put back to `true`. `openWorld` stays true;
these do reach the open web and the catalogue says so.

### 4. Web-AIOS as an MCP server — `/api/harness/mcp` (26 tests)

The inverse of `lib/mcp.ts`. The deterministic tools were already pure and portable by
construction, and keeping them locked in one browser tab wasted that. Point Claude Desktop,
an IDE or another agent at the route and they compute the same numbers from the same
fixtures with the same formulas.

The exposure filter is the load-bearing part. The route has no authentication, by the same
design as `/api/ai/chat`, so only read-only non-destructive tools are reachable — judged
from each tool's own annotations rather than a hand-maintained deny-list a new tool could
be forgotten from. `write_artifact` is not merely filtered: the route never constructs the
writer. A hidden tool and a missing one answer identically, so an unauthenticated caller
cannot enumerate what the deployment holds.

Verified over real HTTP, not just in unit tests:

```
GET  /api/harness/mcp   -> 9 tools, write_artifact absent
initialize              -> protocolVersion 2025-06-18, serverInfo web-aios
tools/call kpi          -> "arr 2026Q1 all = 8,802,000 USD (sum(mrr) * 12 over 3 months, 9 rows, fixtures v1)"
tools/call write_artifact -> -32001 "No tool named write_artifact"
notifications/initialized -> 202, empty body
```

### 5. The trigger layer — Layer 1 finally has a runtime (38 tests)

`src/lib/harness/triggers.ts` (pure) decides *whether* something fires; `harness-triggers.ts`
owns the timers and subscriptions; `kernel/triggers.ts` stores the specs and the decision
ledger; the Harness app gained a Triggers tab.

Five of six harness layers had a runtime and this one did not, so every run in this project
had so far started because a person pressed a button. Three properties carry it:

- **Every decision is recorded, including the refusals, with a reason.** A trigger layer's
  characteristic failure is silence, and a wrong pattern, an event nobody emits and a
  correctly-deduplicated repeat all look identical from outside.
- **Dedupe is mandatory**, over a canonical key that ignores object key order.
- **The clock is injected**, which is why this layer is testable at all rather than
  requiring someone to wait fifteen minutes.

Refusals built in: disarmed by default; one run at a time; a 25-run session ceiling; a
60-second minimum schedule interval enforced in the parser rather than the UI; `/harness/`
writes excluded so a file trigger cannot feed on its own receipts; the `span` event
excluded so a trigger cannot fund itself.

**Verified live in the browser.** Disarmed produced zero attempts. Armed, a matching event
fired with its objective rendered (`Read /notes/a.md and say what changed at 2026-09-16T…`),
an identical payload was suppressed as a duplicate, a different payload fired, a
non-matching event declined with `"unrelated:event" does not match "probe:*"`, a write to
`/notes/probe.md` fired, a write to `/notes-archive/probe.md` declined on the segment
boundary, and a write to `/harness/runs/` produced no attempt at all.

### 6. Swarm ← definition of done and a bidding pass (33 tests)

`dod.ts` and `bid.ts` were written and tested sessions ago and nothing called either. This
is the caller — `src/lib/harness/swarm.ts`, plus the wiring in `apps/Swarm.tsx`.

Every swarm now carries a floor it can fail: at least two agents answered, no agent failed
without a message, the synthesis names disagreement rather than averaging it away, and the
synthesis is substantive. The verdict is written **from the outcomes by code**. It is
deliberately fixed-criteria only: a `judge` criterion would need a model, and the only model
available is the one that just wrote the synthesis — a verifier on the producer's own
weights agrees with it, and that looks exactly like success.

The bidding pass (off by default) ranks agents by measured pass rate and mean cost and
decides who runs *before* spending, rather than letting the live budget stop a swarm
halfway.

**Verified live with no API key.** Three agents errored, synthesis empty, and the swarm
reported *"Did NOT meet its definition of done, score 13%"* naming all three failing
criteria with the evidence. Before today that identical run printed nothing and looked
finished.

**Two real bugs found by these tests:**
- The machine counts the criteria read were being written to `run.transcript`, but every
  fixed check in `dod.ts` reads `run.answer` and nothing reads `transcript`. The criteria
  could never have matched.
- `computeBid` abstains on *any* missing required skill, so handing a formation's agents one
  skill out of two made every agent abstain and the auction award nobody — which is
  indistinguishable from "no suitable agent was found".

### 7. Observatory keeps its trace — `src/kernel/spans.ts`

The span ring was component-local, so closing the window threw away the trace — and the run
you want afterwards is the one that went wrong while you were doing something else. The ring
moved to the kernel and the shell subscribes at boot, so a run started by a trigger while
every window is shut is still recorded. Upsert by id, so the open and close writes of one
span merge instead of duplicating. Not persisted, for the quota reason `kernel/harness.ts`
already documents.

Verified: two spans emitted with Observatory closed, then opened — `Spans (2)`, with the
closing write's cost and duration merged in.

### 8. A new integrity check — duplicate app names

The new app was registered as "Signals" while the Intel app already carried that name. Every
id was unique, so check 2 passed — but the launcher, dock, palette, pin picker and mobile
shell all render the **name**, so the two were indistinguishable everywhere a person
actually chooses between them. Uniqueness of the key is not uniqueness of the label.

Check 4b now catches it, and the check was confirmed to fail on a deliberately injected
collision before being confirmed to pass on the real registry.

The app is now **Open Data** (`id: opendata`).

## What was NOT verified

- **Still no live model call.** No API key was used. Every harness and swarm run in this
  session ended as `failed` with an empty answer, which is the correct behaviour and is
  exactly what the DoD verdicts reported — but the model call itself remains covered only
  by transport tests. This is unchanged from the previous handoff and is still the largest
  gap.
- **Fifteen of the 25 services were not called live.** Wikipedia (direct), arXiv (relayed)
  and Crossref (relayed) were driven against the real providers in the browser and returned
  real data. The other 22 are covered by parser tests against recorded payloads and by the
  URL-construction test, which is not the same as knowing the endpoint still answers.
- **The MCP route was driven by curl, not by a real MCP client.** Claude Desktop, an IDE or
  another agent has not connected to it. The handshake, tool listing, tool call, refusal and
  notification paths were each exercised over real HTTP.
- **No scheduled trigger has fired on its own timer.** Schedule due-ness is covered by 8
  tests against an injected clock, and the poll loop runs every 20s, but nothing in this
  session waited for a real interval to elapse.
- **The bidding pass has no real history to rank on.** Every agent bids on the Laplace
  priors, because no run has ever recorded a per-skill pass. The ranking is tested and
  deterministic; it has never ranked on evidence.
- **The trigger decision ledger records every non-matching event.** That is deliberate —
  silence is what makes Layer 1 undebuggable — but on a chatty bus with several event
  triggers configured, `no_match` entries will crowd out the one that fired. It is capped
  at 300 at write time, so it cannot fill the quota, but it is a readability tradeoff
  rather than a solved problem.
- **Nothing was deployed.** No push, no Vercel build. The production `next build` does pass
  locally, in 114s, with `/api/harness/mcp` in the route table beside the five existing
  handlers — but nothing has run on Vercel, and several bugs in this project's history were
  only visible in the real deployment.
